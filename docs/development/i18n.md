# 国际化与语言包（Issue #135）

本文件规定界面文案的 key 命名、模块划分、社区翻译的导入流程，以及机器校验方式。
规则不是口头约定：`scripts/check-locales.mjs` 会校验仓库里的语言包，`pnpm check` 会跑它。

## 1. 为什么按模块拆语言包

单个 `zh-CN.json` 会变成第二个 `App.vue`：所有并行切片都往里加 key，每次合并都撞车。
因此按模块拆文件，**一个切片只改自己模块的包**，插入点物理分开。

```
apps/desktop/src/locales/
  zh-CN/
    common.json      顶栏 / 通用按钮 / 通用错误前缀
    settings.json    设置页（本切片只含「语言包」区）
    composer.json    输入区 / 发送模式 / 模型选择        （阶段 3）
    session.json     会话区 / 消息 / 工具调用            （阶段 3）
    drawer.json      文件 / Git / 终端 / 搜索抽屉        （阶段 3）
    notify.json      Toast / 通知历史                    （阶段 3）
  en-US/             与 zh-CN 同结构，key 必须完全一致
  index.ts           loader：合并 / 回退 / 切换
  community.ts       社区语言包校验
  packScan.ts        顶层键扫描（CI 与前端共用）
  bootstrap.ts       启动时补读社区语言包
```

阶段 3 起按界面切片逐个建模块（`session` / `composer` 已由 Issue #144 落地，
`drawer` / `notify` 待排期）：**新增模块时同时建 `zh-CN/x.json` 与 `en-US/x.json`，
并在 `locales/index.ts` 的 `BUILTIN_MODULES` 里登记一次**，否则 `check-locales` 会报「多余的模块」。

## 2. key 命名约定

- **扁平 key**，点分段，全小写：`action.copy`、`nav.search.open`、`locale.imported.ok`。
- 包内 key 至少两段（`action.copy`），强制「动作 + 对象」，也顺手挡掉整包只写一个 key 的残包。
- 组件里写的是**合并后的 key**：`t("common.action.copy")` —— 模块名 + 包内 key，
  一眼能看出该去哪个文件改文案。
- 语言包是纯 JSON，不含逻辑；日期与数字用 `Intl`（`formatNumber` / `formatDateTime`），不写死格式。
- 内部日志、代码注释、开发者面向的 CLI 输出**不翻译**。

## 3. 三条强制规则

1. **一个切片只允许改自己模块的 json。**
2. **禁止跨模块重复定义 key。** 终端抽屉要复用「复制」，写 `common.action.copy`，
   不要在 `drawer.json` 里再写一遍 `action.copy`：两个模块同名会让社区翻译对不上。
   这条在启动阶段由 `buildLocaleMessages` 抛 `LocaleConflictError`，CI 由 `check-locales` 拦。
3. **新增模块时同时建两份文件并在 loader 登记**，两个语言的 key 集合必须完全一致。

## 4. loader 行为

```ts
const { t, locale, setLocale, formatNumber, formatDateTime } = useLocale();
```

- `useLocale()` 是**应用级单例**：所有组件共享同一份 `locale` 与 `messages`，
  否则切语言只会有半个界面跟着变。
- `messages` 是 `shallowRef`：`setLocale` 只换表，**不重建组件**，用到 `t()` 的模板自动重渲染。
- 缺失 key **回退 `zh-CN`**；两边都没有时原样返回 key（比空白更容易被发现）。
  开发模式（`import.meta.env.DEV`）下每个缺失 key 只 `console.warn` 一次，不刷屏。
- 插值只替换已知参数：`t("settings.locale.failed", { reason })` → `导入失败：…`；
  未提供的 `{reason}` 原样保留，便于发现漏传。
- 内置语言包在**模块加载时**就合并完成：key 冲突与格式错误会让应用启动失败——这是有意的，
  静默覆盖会让社区翻译在没有任何提示的情况下失效。

## 5. 语言偏好

- 存储键 `soxu.locale`（`apps/desktop/src/settings/locale.ts`），只存一个短标签。
- 初始语言：持久化偏好 → 系统语言（`zh*` → `zh-CN`、`en*` → `en-US`）→ `zh-CN`。
- 脏值（`zh_CN`、`../../evil`、超长）当作没有偏好，不抛错。
- 上次选的是社区语言包时，`bootstrap.ts` 在挂载后异步补读；
  读不到就回退中文且**不覆盖偏好**（用户把包放回去，下次启动仍然是他选的语言）。

## 6. 社区翻译流程

### 6.1 提交进仓库（成为内置语言）

1. 设置 → 扩展 → 语言包 → 「复制」，得到基准包 JSON（按 key 排序，便于 diff）；
2. 翻译后放进 `apps/desktop/src/locales/<tag>/`，按模块拆文件；
3. 在 `locales/index.ts` 的 `BUILTIN_MODULES` 与 `settings/locale.ts` 的 `BUILTIN_LOCALES` 登记；
4. `node scripts/check-locales.mjs` 必须通过（key 与 `zh-CN` 完全一致）。

### 6.2 导入到本机（不改代码）

1. 复制基准包 → 翻译 → 存成 `<tag>.json`（如 `ja-JP.json`，**文件名就是语言标签**）；
2. 设置 → 扩展 → 语言包 → 「导入语言包」，选该文件；
3. 校验通过后写入应用数据目录的 `locales/` 子目录，并立即出现在语言列表里。

导入校验（`locales/community.ts`，失败会逐条说明原因）：

| 规则 | 说明 |
| --- | --- |
| 合法 JSON 对象 | 顶层必须是 `{ "key": "文案" }` |
| key 是基准包的**子集** | 缺的 key 回退 `zh-CN`，多出来的 key 会被拒绝 |
| 值非空 | 空字符串/纯空白都算未翻译 |
| 无重复 key | 自己扫原文，不依赖 `JSON.parse`（它会静默取最后一个） |
| 标签合法且不覆盖内置 | `ja-JP` 可以，`en-US` 不行 |
| 大小上限 | 256 KiB（前后端各自校验） |

落盘位置：

| 平台 | 路径 |
| --- | --- |
| Windows | `%APPDATA%\dev.soxu.desktop\locales\<tag>.json` |
| macOS | `~/Library/Application Support/dev.soxu.desktop/locales/<tag>.json` |
| Linux | `~/.local/share/dev.soxu.desktop/locales/<tag>.json` |

**不写入仓库、不随更新丢失**：更新应用只替换程序文件，用户导入的语言包留在应用数据目录；
「移除」按钮删掉对应文件并清掉内存注册，正在使用的包会先回退到 `zh-CN`。

后端命令（`extension` 领域块，见 `docs/development/command-blocks.md`）：

| 命令 | 作用 |
| --- | --- |
| `list_locale_packs` | 返回目录路径与已导入的标签（字母序） |
| `read_locale_pack` | 读取一个已导入包的原文 |
| `save_locale_pack` | 写入（覆盖）；先写临时文件再改名，失败不会留下半个 JSON |
| `delete_locale_pack` | 删除；返回是否真的删掉了 |
| `read_locale_source` | 读取用户选中的源文件（只放行 `.json`，有大小上限） |

语言标签会拼进文件名，因此 `locale_store::validate_tag` 只允许 ASCII 字母数字与 `-`、
且必须以小写字母开头——这是路径穿越的唯一防线，前端与后端各自校验一次。

## 7. CI 校验

```powershell
node scripts/check-locales.mjs      # 仓库根目录，或 node scripts/check-locales.mjs <root>
pnpm check                          # 门禁里已经包含这一步（CI 的 quality 作业会跑）
```

脚本做四件事：

1. 内置语言目录齐全（`zh-CN` / `en-US`），模块集合一一对应；
2. 每个模块的 key 集合在两个语言里**完全一致**；
3. key 形状合法、文案非空、同一文件内无重复 key；
4. 同一语言内不出现**跨模块同名 key**。

失败信息会指出文件与具体 key，例如：

```
❌ apps/desktop/src/locales/en-US/common.json 缺少 1 个 key（zh-CN 有）：action.copy
```

社区导入的语言包**不进 CI**：它们不在仓库里，导入时由 `locales/community.ts` 校验。
`.github/workflows/` 属于受保护路径，本切片没有修改它；校验通过 `pnpm check` 进入 CI。

## 8. 三段式排期

| 阶段 | 内容 | 状态 |
| --- | --- | --- |
| 1. 框架 | loader + 目录结构 + `common` 完整迁移 | 本切片（Issue #135） |
| 2. 强制 | 新切片的所有用户可见文案必须走 `t()` | 见第 9 节 |
| 3. 存量迁移 | 会话区 / 输入区（Issue #144）已完成；设置页 / 搜索抽屉 / Git 抽屉 / 通知待排期 | 进行中 |

不做一次性全量迁移的理由：把四五个界面的文案抽离压成一个大 PR，改动面几百处，
review 质量必然下降，还会和正在跑的切片冲突。分批迁移每个任务只改一个界面，机械且可验证。

## 9. 「新增文案必须走 t()」的约定

约定内容（阶段 2 起对所有切片生效）：

- 新增的用户可见文案**不得**在 `.vue` / `.ts` 里硬编码，必须走 `t()`；
- 只能改自己模块的语言包；需要复用别处文案时引用已有 key，不复制；
- 新增 key 必须同时出现在 `zh-CN` 与 `en-US`，否则 `pnpm check` 失败；
- 无障碍名称（`aria-label`、`aria-description`）与 tooltip 文案同样属于用户可见文案。

**这条规则的正式落点是 `agents/policies/coding-standards.md`，属于受保护路径**：
开发 Agent 不得自行修改，需维护者审核后单独提交。本切片只在本文件与
`docs/development/command-blocks.md` 同级的位置给出约定，并在 PR 中说明待批准事项。

## 11. 已知边界

- 桌面端真实导入流程（系统文件对话框 → 写入 `%APPDATA%` → 重启后仍生效）**未在本切片实机验证**，
  需要 `pnpm tauri:dev` 手工走一遍；Node 测试覆盖的是校验、编排与失败路径。
- `en-US` 目前覆盖 `common`、`settings.locale.*`、`session.*`（会话区）与 `composer.*`（输入区）；
  侧栏、抽屉、通知与 loop 控制台仍是中文，属阶段 3 的剩余任务。
- 社区包若把 `common.copy` 这类带前缀的 key 抄进另一个模块，运行时会报冲突；
  但「同一段文案在两个模块用不同 key 各写一遍」无法机器判定，只能靠 review 与第 3 节规则。
- 浏览器预览（无 Tauri）下导入按钮禁用并说明原因，不会用假数据冒充成功。
